# OpenHCL 7.3.4: OpenVMM emulation and VMM-test validation

Date: 2026-11-23.

## Result

**The upgraded kernel boots as OpenHCL in VTL2, starts VTL0 userspace, and passes
six selected OpenVMM VMM tests on Windows Hypervisor Platform (WHP).**

The same OpenVMM main's packaged-kernel control also boots successfully and
passes the VMM boot test. No upgraded-kernel functional regression surfaced in
these checks. No kernel runtime patch was added to obtain these passes.

A separate, reproducible defect in OpenVMM main's custom-kernel test tooling was
fixed and validated. It prevented test setup before a VM could be created; it
was not a failure of the upgraded kernel.

These are non-confidential x64 emulation results, not native Hyper-V, TDX/SNP
hardware, ARM64 runtime, full-suite, or production qualification.

## Method and controls

The workflow follows the requested Linux-direct IGVM plus Windows/WHP route
from WSL:

1. Build the Windows-target OpenVMM and the Linux-direct OpenHCL IGVM from the
   pinned latest main.
2. Embed the upgraded standard x64 kernel and its matching modules using
   `--custom-kernel` and `--custom-kernel-modules`.
3. Run Windows OpenVMM with `--hv --vtl2` and capture both serial consoles.
4. Repeat with the kernel packaged by the same main, using the same two virtual
   CPUs, 2GB RAM and Linux-direct guest for the manual comparison.
5. Run the repository's Petri/nextest VMM workflow with the custom kernel and
   verify agent connection, test assertions, guest power-off and teardown.

The manual target and control IGVMs contain byte-identical `openvmm_hcl` and
`openhcl_boot` components:

- OpenHCL userspace SHA-256:
  `e97e1abd1f73c7940c431f1c2d366ffd2c2e6c65c26f0c3108c51b26b425875f`
- OpenHCL bootshim SHA-256:
  `6148a5b48cc6b4272ed2a369f7b6d06fdb538bfe90c9b23de6724cf00a2164b0`
- Upgraded VTL2 kernel SHA-256:
  `c70e31b415f6734d6db819593dd7569cc20bcde4f3afd6db3958aa6329e0704b`

Compiler debug information and incremental compilation were disabled for these

make emulation pass. The newer target's generated defaults, including its
preemption default, remain as requested.

### Representative build and launch

From the isolated OpenVMM main checkout:

```bash
. build_support/setup_windows_cross.sh

KERNEL_OUT=/home/namjain/openvmm/OHCL-Linux-Kernel.worktrees/draft-7.3.4-upgrade/kernel/out/build/native/bin/x64

cargo xflowey build-igvm x64-test-linux-direct \
  --custom-kernel "$KERNEL_OUT/vmlinux" \
  --custom-kernel-modules "$KERNEL_OUT/modules"
```

The kernel's package directory must include `kernel_build_metadata.json`; an
archived standalone `vmlinux` without that sibling metadata is insufficient.

Latest main requires explicit IGVM firmware/personality syntax:

```bash
cargo run --target x86_64-pc-windows-msvc -- \
  --hv --vtl2 \
  --igvm "firmware=<Windows path to custom IGVM>,personality=openhcl" \
  --memory 2GB --processors 2 \
  --com1 none \
  --com3 "file=<Windows path to VTL2 log>" \
  --vmbus-com1-serial "file=<Windows path to VTL0 log>" \
  --guest-reset-action exit:90 \
  --guest-crash-action exit:91 \
  --guest-shutdown-action exit
```

The recorded actual command arrays, converted Windows paths, timestamps and
IGVM hashes are in the [runtime evidence JSON](../../runtime-validation/results.json).
File-backed serial logging replaces separate GUI terminals only for automated
capture; both VTL consoles were observed.

## Observed manual boot milestones

Both target and control runs:

- booted the expected VTL2 kernel;
- initialized OpenHCL and started the same VTL0 Linux kernel;
- brought up two VTL0 CPUs;
- reached the VTL0 init process and its initrd shell;
- had no observed VTL2 panic, oops or general-protection fault;
- stopped the VM and its worker cleanly after the observation.

The diskless manual guest reports a missing root device before dropping into
its initrd shell. This is expected for this invocation and is not treated as an
installed-root-filesystem boot pass. The VMM tests provide stronger agent and
I/O validation than this shell milestone alone.

## Problems surfaced and their disposition

### Fixed: latest-main custom-kernel VMM recipe identity

**Location:** OpenVMM's
[`local_build_and_run_nextest_vmm_tests.rs`](../../../../openvmm.worktrees/main-7.3.4-validation/flowey/flowey_lib_hvlite/src/_jobs/local_build_and_run_nextest_vmm_tests.rs),
with CLI wiring in
[`vmm_tests_run.rs`](../../../../openvmm.worktrees/main-7.3.4-validation/flowey/flowey_hvlite/src/pipelines/vmm_tests_run.rs).

Before the fix, supplying a custom kernel replaced the well-known test recipe
with `LocalOnlyCustom`. That made the build return
`OpenhclIgvmOutput::LocalOnlyCustom`, but
[`init_vmm_tests_content_dir.rs`](../../../../openvmm.worktrees/main-7.3.4-validation/flowey/flowey_lib_hvlite/src/init_vmm_tests_content_dir.rs)
expects the original recipe-specific variant, such as `X64TestLinuxDirect`.
Artifact staging failed before creating a VM.

The fix keeps the original recipe and uses the existing
`cfg_versions::LocalKernel` override for the kernel, modules and metadata. It
also rejects an incomplete kernel/modules override instead of silently ignoring
one half.

Fix commit: `dd164fd14c593f19cc554b582b3227de8922ee2d`, on the isolated OpenVMM
validation branch. This is a tooling defect in latest main, not a new-kernel
regression.

### Environment adjustment: socket path length

The first staged VMM test failed before VM creation because its long WSL UNC
temporary path exceeded the AF_UNIX `SUN_LEN` limit. The supported `--dir`
option moved test output to short Windows paths under
`C:\Users\namjain\ov734-tests`, `ov734-boot` and `ov618-tests`.

No kernel or socket-library workaround was added. This is why these WSL runs
explicitly override the otherwise suitable default output directory.

### Extra target warning: synthetic-timer fallback

The initial warning-signature comparison found one additional kernel warning:

```text
Hyper-V: stimer setup failed with error -22
```

It comes from [hv_init.c](../arch/x86/hyperv/hv_init.c), after
[hyperv_timer.c](../drivers/clocksource/hyperv_timer.c) rejects missing synthetic
timer/direct-mode capabilities. Upstream commit `be0cfab740e58` deliberately
removes legacy message-mode synthetic-timer delivery, emits this diagnostic and
retains the LAPIC timer fallback.

The target continues to boot and passes the selected reboot, I/O and servicing
tests. This is recorded as an upstream/emulator capability difference, not
silenced or "fixed" by restoring obsolete code. It does not establish
performance parity between timer implementations.

SRSO-policy warnings, PM-timer-assist warnings and the deprecated `panic_print`
parameter message also occur in the control. They are not attributed to the
7.3.4 port.

### Invocation corrections, not kernel fixes

- The first packaging attempt used a binary-only archive directory without
  `kernel_build_metadata.json`; using the complete build output fixed it.
- The first test filter used a conceptual recipe name instead of the actual
  registered test name; exact-name discovery corrected the selection.

These unsuccessful setup attempts remain in the local logs. They are not
reported as failed kernel boots, successful tests, or new kernel regressions.

## Confidence after this work

Confidence is materially stronger than compilation alone:

- all three supported kernel build configurations pass;
- upgraded x64 OpenHCL boots and runs VTL0 under WHP;
- selected networking, storage, alias-map, reboot and three-cycle servicing
  tests pass;
- the packaged control passes boot;
- the one required source fix is isolated to test tooling and has a regression
  test and before/after integration evidence.

**Assessment: a tested emulation candidate, not release sign-off.**

Still required:

- native Hyper-V VTL validation;
- real TDX, SEV-SNP and Secure AVIC hardware tests;
- ARM64 boot/runtime validation;
- sidecar-specific, CPU/hotplug and broader memory/concurrency stress;
- cross-version servicing/upgrade/downgrade;
- long-duration, performance, security-policy and full regression review.

No upgraded-kernel functional regression was confirmed by this bounded test
campaign. That is not proof that the rest of the OOT stack is defect-free.
