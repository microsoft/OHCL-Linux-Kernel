# OpenHCL Linux 7.3.4 upgrade: confidence assessment

Assessment date: 2026-11-23.

## Executive assessment

**The branch is ready for platform validation, not release sign-off.**

Compilation confidence is now high for the repository's supported kernel
matrix: standard x64, CVM-x64, and standard ARM64 all compile and link, including
modules and header installation. The earlier gap in CVM compilation coverage
has been closed: the combined CVM configuration enables and builds TDX,
SEV-SNP, and Secure AVIC support.

Functional confidence remains moderate and provisional, but is no longer based
only on compilation. Windows/WHP emulation boots the upgraded OpenHCL kernel in
VTL2 and reaches VTL0 userspace; six selected VMM tests pass, including storage,
networking, alias mappings, reboot and three same-version servicing restarts.
The packaged-kernel control also passes boot. Native Hyper-V, ARM64 runtime,
confidential-computing hardware, broader stress and performance remain unverified.

See the [runtime test and fix report](./7.3.4-openvmm-runtime-report.md) for exact
commands, controls, test results and the separately validated OpenVMM tooling fix.

No numerical probability of correctness is justified by the evidence.

### Concrete feature coverage

All three configurations enable `HYPERV_VTL_MODE`, `MSHV_VTL` and transparent
huge pages. Standard ARM64 retains its 4KB-page configuration.

The CVM-x64 configuration additionally enables:

- `INTEL_TDX_GUEST` and `TDX_GUEST_DRIVER`;
- `SEV_GUEST` and `AMD_MEM_ENCRYPT`;
- `AMD_SECURE_AVIC`;
- ACPI, while retaining the source's non-EFI OpenHCL configuration.

The build evidence includes the common mshv_vtl driver, x64 sidecar code,
TDX entry assembly, CVM local mappings, TDX/SEV core code, Secure AVIC, and the
TDX/SNP guest drivers. The ARM64 build includes its Hyper-V VTL platform code
and mshv_vtl driver.

This does not claim that every optional runtime branch was executed or every
module/built-in permutation was tested. ARM64's empty CVM fragment does not
constitute a separate confidential ARM64 implementation or validation result.
The perf initramfs manifest is not another kernel configuration, and perf
tooling was not rebuilt in this follow-up.

## Configuration migration

All five Microsoft configuration inputs initially matched the pinned final
6.18 source byte-for-byte. The existing build workflow generated the final
7.3.4 configurations.

- [hcl-x64.config](../Microsoft/hcl-x64.config) is standard x86-64 only.
- [hcl-arm64.config](../Microsoft/hcl-arm64.config) is standard ARM64 only.
- [x64-cvm.config](../Microsoft/x64-cvm.config) is the separate CVM-only delta,
  generated from the successful standard and CVM configurations.
- [arm64-cvm.config](../Microsoft/arm64-cvm.config) remains empty.
- [hcl-rootfs-perf.config](../Microsoft/hcl-rootfs-perf.config) remains unchanged;
  it describes an initramfs file, not Kconfig selections.

The separate CVM fragment was merged with the final standard x64 configuration
and processed with target olddefconfig. A symbol-by-symbol comparison with the
successfully compiled CVM configuration produced **no differences**.

### Target defaults retained, not 6.18 defaults forced

The generated 7.3.4 defaults are retained as requested. The most important
observed behavioral change is:

| Setting | 6.18 seed | Final 7.3.4 configuration |
|---|---|---|
| Default preemption model | `PREEMPT_NONE=y` | `PREEMPT=y` |
| Dynamic preemption infrastructure | `PREEMPT_DYNAMIC=y` | `PREEMPT_DYNAMIC=y` |

Upstream commit `7dadeaa6e851e` deliberately restricts NONE on these
lazy-preemption-capable architectures and rejects the corresponding boot
parameter there. No downstream scheduler compatibility patch was added. The
user explicitly chose to retain the newer defaults and review the configuration
changes later.

This is a real scheduling-policy change. It requires review and workload
validation before claiming equivalent latency, throughput, or idle behavior.
Other newly emitted/removed symbols and toolchain-generated values are recorded
in the configuration-refresh section of the
[manifest](./7.3.4-port-manifest.json) and the detailed
[port review](./7.3.4-port-review.md).

## Problems found and fixed by compilation

### Standard x64 decrypted-BSS linker failure

The initial standard x64 build found references to decrypted-BSS symbols that
the target linker script emits only when AMD encryption is enabled.

Fix `6ff96af2dc81` guards the gap-address declarations and freeing operation with
the same configuration condition. The standard configuration was not changed
to enable encryption just to make the link pass.

### Real CVM-x64 non-EFI linker failure

The first CVM-x64 link exposed an unconditional AMD selection of EFI-only
unaccepted-memory support, despite the OpenHCL CVM configuration disabling EFI.
The link failed with undefined references to the EFI global object.

Fix `41bf5aa0dad32` makes the selection conditional on its actual EFI_STUB
dependency. It retains the existing non-EFI OpenHCL selections and preserves
EFI-backed support when EFI_STUB is enabled. The successful CVM retry has no
unmet-dependency warnings or compiler warnings.

The runtime implications still need hardware validation, especially memory
acceptance and provisioning assumptions. A successful link does not prove that
every hypervisor memory-provisioning mode is handled.

### Remaining warning

ARM64 reports that the non-x86
`mshv_create_apicid_to_cpuid_mapping()` stub is defined but unused. The build
passes; the warning is documented and was not hidden with compiler flags.

## What is not established yet

Beyond the selected x64 WHP tests, this task does not establish:

- native Hyper-V VTL boot or ARM64 runtime behavior;
- successful TDX or SEV-SNP boot on actual isolated hardware;
- exhaustive VTL0/VTL1 register-state or timer/interrupt correctness;
- correct sidecar lifecycle, CPU cancellation and completion semantics;
- mmap/GUP/folio correctness under concurrency or the expected page-table
  memory bounds for large VTL0 mappings;
- broad VMBus, vPCI, VFIO, storage, network or UIO coverage beyond the selected
  MANA and storvsp emulation tests;
- correct shared/private memory conversion or acceptance during servicing;
- cross-version servicing, long-run lifecycle or memory/CPU hotplug behavior
  beyond the bounded reboot and same-version servicing checks;
- acceptable latency, throughput, idle behavior or long-run stability with the
  new scheduling defaults;
- reproducible release packaging or compatibility with the separately supplied
  iommufd-cdev-v2 binary-release variant.

No independent reviewer, kernel KUnit/selftest campaign, sanitizer run, broad
stress suite or performance benchmark was used as evidence. The 42 passing
Flowey package unit tests validate the tooling fix, not kernel source coverage.

## Recommended promotion gates

1. **Configuration and code review.** Review all 21 conflict resolutions,
   consequential skips, the EFI dependency fix and the generated config delta,
   especially the preemption model. Confirm intended module and security
   selections for the actual product deployment.
2. **Native platform boot.** Extend the successful x64 WHP boots to native
   Hyper-V and ARM64; inspect boot logs and exercise the core UAPI.
3. **CVM boot on both vendors.** Separately validate TDX and SEV-SNP, including
   Secure AVIC where supported, private/shared mappings, acceptance and guest
   register state. A combined compile is not a substitute for these two runs.
4. **Targeted functional stress.** Exercise sidecar start/run/stop and
   cancellation; concurrent VTL0 mmap/GUP/direct I/O; 4KB/2MB mapping boundaries;
   interrupts, timer deadlines and CPU targeting. Check correctness and page
   table growth rather than just absence of a build failure.
5. **Servicing and regression.** Run the product's save/restore/live-servicing
   workflow, storage/network/device workloads and relevant hotplug tests; compare
   results and performance with the known-good 6.18 release.
6. **Release workflow.** Validate the intended Nix/CI packaging and, if required,
   reproducibility, then obtain independent review before promotion.
